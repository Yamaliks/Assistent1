# Assistent1

Локальный персональный ассистент для Windows 10/11. **Этапы 1–2: интерфейс и пользовательские команды.**
Tauri 2 · React · TypeScript · Tailwind CSS · Rust · Lucide. Дизайн Graphite Purple.

## Запуск интерфейса

Нужен Node.js 22.18+ (или 24 LTS) и npm:

```sh
npm ci
npm run dev
```

Vite использует порт 1420. Параметр `?window=palette` открывает интерфейс панели для проверки в браузере.
В браузере глобальная горячая клавиша и нативные окна недоступны; панель открывается кнопкой.
Шрифт Inter используется при наличии на устройстве, иначе Segoe UI/system-ui. Удалённые шрифты не загружаются.

## Windows-приложение

Чтобы получить установщик без локальной установки Rust/Node.js, используйте
[инструкцию GitHub Actions](WINDOWS_BUILD.md). Workflow собирает Windows x64 NSIS и сохраняет `.exe` как artifact.

Установите Rust stable 1.90+ (MSVC), Microsoft Visual Studio Build Tools с компонентом «Desktop development with C++»
и Windows SDK, а также Microsoft Edge WebView2 Runtime. Затем:

```sh
npm ci
npm run tauri dev
```

Главное окно: 1180×760. Единственная быстрая панель: 560px, без рамки, скрыта при запуске.
`Ctrl+Alt+Space` показывает существующую панель, `Esc` скрывает её. Если комбинация занята,
регистрация завершит запуск ошибкой — освободите комбинацию и повторите запуск.
Повторный запуск EXE фокусирует уже открытое приложение: новые окна и экземпляры не создаются.
Крестик скрывает главное окно в трей, сохраняя окно и процесс. Двойной левый клик по иконке
или «Открыть Assistent1» восстанавливает окно и запрашивает фокус. Меню также открывает панель команд;
«Выход» полностью завершает приложение. Повторный EXE показывает тот же экземпляр.

```sh
npm run tauri build
```

NSIS-установщик появится в `src-tauri/target/release/bundle/nsis/`.
Windows-сборку и поведение нативных окон необходимо проверять на Windows; Linux-проверка интерфейса этого не заменяет.

## Проверки

```sh
npm test
npm run build
cargo test --locked --manifest-path tests/rust-validation/Cargo.toml
```

При доступном Rust toolchain: `cargo fmt --manifest-path src-tauri/Cargo.toml -- --check` и
`cargo check --manifest-path src-tauri/Cargo.toml`. На Linux дополнительно нужны системные зависимости
Tauri (GTK 3, WebKitGTK 4.1 и другие пакеты из официальной документации), графическая сессия для запуска.

Проверено в текущей Linux-среде: чистая установка `npm ci`, TypeScript/Vite-сборка, 11 тестов TypeScript и 6 тестов Rust (валидация и жизненный цикл окна),
проверка UI в Chromium (навигация, миграция настроек, создание/редактирование/удаление команд, синхронизация окон и поиск),
Rust formatting и `cargo check --locked --manifest-path src-tauri/Cargo.toml --target x86_64-pc-windows-gnu`
с Rust 1.99 и MinGW. Проверка типов для Windows не создаёт EXE или установщик.
Реальный запуск EXE, браузера и папок, нативная горячая клавиша, жизненный цикл окон и установщик ещё требуют проверки на Windows.

## Что работает сейчас

- Главная, Режимы, Команды, История, Голос и Настройки, адаптивный интерфейс.
- Карточки и черновики режимов, изменение названия/описания/иконки/фразы.
- Локальное версионированное сохранение и синхронизация настроек между окнами через Web Storage.
- Пользовательские команды: создание, изменение, удаление с подтверждением и локальное сохранение.
- Быстрая панель: поиск, запуск отдельных команд по карточке, названию или фразе; просмотр режимов и навигация.
- Rust: проверка и запуск существующих EXE без аргументов, открытие HTTP(S)-сайтов и локальных папок через Windows.
- Ошибки запуска отображаются пользователю; повторные клики блокируются до ответа. Успех означает принятие запроса Windows, не проверку здоровья приложения.
- Два окна в одном Tauri-процессе; дизайн и горячая клавиша сохранены.

**Ещё не работают:** выполнение режимов, проверка процессов,
редактор действий, история выполнения, громкость/ночной свет, голос, активационная фраза и автозапуск.
Ни одно приложение не считается установленным: стартовые режимы имеют пустые действия.
Кнопки режимов открывают просмотр и не управляют системой.

## Архитектура

- `src/domain/modes.ts` — типизированные режимы и действия.
- `src/services/commandRouter.ts` — текст → разрешённая команда; неизвестные строки отклоняются.
- `src/domain/commands.ts` — типизированные пользовательские команды и проверки адресов.
- `src/services/modeEngine.ts` — выполнение одной пользовательской команды через System Services; режимы пока только для просмотра.
- `src/services/systemServices.ts` — проверка и вызов Rust через IPC, обработка ошибок.
- `src/services/voiceService.ts` — контракт локальной речи, без доступа к микрофону.
- `src/services/settingsStorage.ts` — схема v2, миграция из v1, валидация и обработка ошибок хранилища.
- `src-tauri` — окна, минимальные capabilities, горячая клавиша и нативные Windows-действия; shell-плагина нет.
- `tests/rust-validation` — Linux-совместимый harness, тестирующий тот же модуль проверки адресов, который использует Windows backend.

Настройки находятся в локальном профиле WebView. Браузерный и Tauri-профили независимы.
При повреждённых данных показывается предупреждение и временные примеры; до явного сохранения
исходные данные не перезаписываются. Облачных API, аналитики и сетевого распознавания нет.
Планы следующих этапов — в ROADMAP.md, правила разработки — в AGENTS.md.

## Настройка команд (этап 2)

Откройте «Команды» → «Добавить команду». Укажите имя, тип, цель и необязательную фразу.
EXE: полный путь, например `C:\Windows\System32\notepad.exe`, без кавычек и аргументов.
Сайт: `https://example.com`. Папка: существующий локальный путь, например `C:\Users\Имя\Documents`.
Названия и фразы не должны совпадать с режимами, другими командами или словами навигации.
Команду можно запустить из списка или из панели (`Ctrl+Alt+Space`) по карточке/точному имени/фразе + Enter.
В браузерном просмотре системные действия отклоняются с явным сообщением.

Backend повторно проверяет данные независимо от UI: запрещены управляющие символы, сетевые/служебные пути,
не-EXE программы, shell-строки и опасные схемы URL. Ссылки с логином/паролем в адресе не поддерживаются.
Пути канонизируются; ссылка на удалённый ресурс через junction тоже отклоняется.
Сайты и папки открываются через `ShellExecuteW` с `open` и без параметров; это Windows API ассоциаций,
а не выполнение командной строки. Отсутствующие пути, неверный тип файла, отказ доступа и ошибки ассоциации
возвращаются в интерфейс. Администраторские EXE могут требовать повышения прав: приложение его не запрашивает.
Никакие процессы не закрываются. Повторный отдельный запрос может запустить ещё один экземпляр программы;
обнаружение уже работающих процессов относится к будущему движку режимов.

Старые настройки v1 читаются без перезаписи; при явном сохранении пишется v2 с пользовательскими командами.
Ключ хранилища сохранён для миграции. Проверка сохранения не означает, что файл уже существует:
Windows проверяет его при выполнении. Изменение команды обновляется в другом окне через событие storage.

## Проверка исправления трея (0.1.1)

Перед обновлением завершите старый зависший Assistent1.exe через Диспетчер задач, если у него нет трея.
После установки проверяйте:

1. Первый запуск показывает главное окно и одну иконку трея.
2. Крестик / Alt+F4 скрывает главное окно, сохраняя приложение в трее.
3. Двойной левый клик и «Открыть Assistent1» восстанавливают окно поверх других окон.
4. Повторный EXE после скрытия или сворачивания открывает тот же экземпляр. Второй запускаемый процесс быстро завершает работу.
5. «Открыть панель команд» и Ctrl+Alt+Space показывают существующую панель. Esc/Alt+F4 скрывают её.
6. «Выход» удаляет иконку трея и завершает процесс; следующий запуск снова показывает главное окно.

Dev и release используют одну реализацию жизненного цикла без `cfg(debug_assertions)` и один Windows mutex
по `com.assistent1.desktop`. Для независимой проверки сначала завершайте другой вариант через «Выход».
В dev нужен запущенный Vite (`npm run tauri dev`); release содержит собранный интерфейс и не требует сервера.
Главное окно скрыто только на время создания WebView и регистрации обработчиков; завершающий шаг setup
безусловно показывает его в обоих вариантах. Это исключает закрытие ещё не готового HWND при запуске.
Различие `windows_subsystem` в release только скрывает консоль, но не меняет окна или поведение трея.
CI проверяет debug/dev-конфигурацию, собирает release и проверяет реальное закрытие/повторное открытие HWND
через `tests/windows-reopen.ps1`, если runner имеет интерактивную оболочку Windows. При её отсутствии smoke
явно пропускается с предупреждением. Двойной клик, меню «Выход», фокус и горячая клавиша требуют проверки на ПК.
