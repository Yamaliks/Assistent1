### UX Bugfix — сохранение действий и простые команды (готово)

- Причина потери: выбранная ссылка оставалась в React-черновике, библиотека записывалась отдельно. Добавление приложения/сайта теперь сохраняет библиотеку и режим одной записью сразу; повторная ссылка не добавляется.
- Проверка совпадений EXE (регистр/разделители Windows) и нормализованного URL при создании; предложение выбрать существующий элемент. Старые дубликаты и данные не удаляются автоматически.
- Команды: название/тип, выбор из библиотеки или системный EXE-диалог, ручные URL/папки, предложение сохранить новый элемент в библиотеку без копий. Самостоятельный запуск и выбор команд в режиме сохранены.
- Карточки команд с «Запустить» и меню «…»; дополнительные параметры скрыты. Уточнены пояснения разделов.
- Формы используют сжимаемые колонки и перенос кнопок; на узком окне поля/кнопки располагаются вертикально.
- Точечные тесты проверяют атомарное сохранение, повторное добавление, дубликаты, создание через режим и команды, выбор EXE и прежний запуск. Windows-диалог/вёрстка требуют проверки в установленном приложении; CI и установщик не запускались.

### 3В-Lite — запуск режимов (готово)

- В режиме выбираются существующие приложения/сайты; создание и редактирование — в библиотеке. Кнопка перехода и возврат в режим сохраняют настройки и обновляют список.
- «Запустить режим» сохраняет текущие действия и запускает их последовательно через прежние System Services/Rust; отключённые действия пропускаются.
- EXE/сайты по ID библиотеки, папки, сохранённые команды и старые inline-действия поддерживаются. Не настроенные/отсутствующие пути и ошибки запуска не прерывают остальные шаги.
- Защита повторного запуска по ID режима, ход выполнения, результаты и итог «Готово»/«Есть ошибки». Последний итог сохраняется с режимом в прежнем хранилище v4.
- Для браузера по умолчанию требуется действие сайта с адресом; запуск браузера без адреса не поддержан прежним сервисом. Ночные системные действия остаются недоступными.
- Палитра сохраняет запуск отдельных команд; запуск режима выполняется в главном редакторе. Трей, single-instance и Rust не менялись.
- Подтверждённый успех означает успешный ответ службы запуска, а не ожидание закрытия/проверку процесса. Windows CI/установщик вручную не запускались.

### 3Г — палитра и запуск с карточек (готово)

- Палитра восстанавливается через UI-очередь show → unminimize → focus; повторная горячая клавиша использует то же окно и возвращает фокус в поиск. Регистрация сочетания и первый single-instance плагин сохранены; ошибка регистрации остаётся явной ошибкой запуска.
- Главная/режимы: независимые «Запустить» и «Настроить». Палитра ищет режимы, команды, приложения и сайты; запускает по Enter, скрывается по Esc.
- Единственный исполнитель режимов — главное окно (включая скрытое в трей). Палитра передаёт только ID через события Tauri; прогресс, итог и изменения настроек синхронизируются. Один замок защищает от запуска из обоих окон.
- «Запускать приложения свёрнутыми» по умолчанию выключено; для EXE используется Windows ShellExecute с SW_SHOWMINNOACTIVE без аргументов и поиска чужих окон. Сторонние программы могут игнорировать запрос.
- Браузер без URL: EXE системной http-ассоциации через AssocQueryStringW, запуск без параметров. Если Windows не предоставляет такой EXE, показана инструкция выбрать браузер EXE в библиотеке. Сайты открываются обычной ассоциацией HTTP(S).
- Требуют проверки на Windows: конфликт/фокус Ctrl+Alt+Space после трея и повторного EXE, особенности системной ассоциации браузера и свёрнутого запуска разных приложений. Windows CI вручную не запускался.

### SOL Core — частично: A и B готовы к проверке на Windows

- A: браузер по умолчанию проверяет свой EXE перед запуском, не создаёт новое окно/вкладку при достоверном совпадении. Конкретные сайты открываются независимо.
- Для приложений — «Не запускать повторно, если уже работает» (выключено по умолчанию); режимы, палитра и команды используют общую настройку. Windows-кандидаты проверяются по полному каноническому пути EXE с PROCESS_QUERY_LIMITED_INFORMATION. Одинаковое имя процесса не считается доказательством. Недоступные совпадающие кандидаты дают понятную ошибку без повторного запуска. Свои проверки/запуски сериализуются; внешние запуски и приложения-лаунчеры всё равно требуют проверки на Windows.
- Статусы: «Запущено», «Уже работает», «Пропущено», «Ошибка». Свёрнутый запуск сохранён; сторонние программы могут игнорировать запрос.
- B: создание режима с любым названием, пустым списком или шаблоном; независимые ID, выбор/изменение иконки, переименование, подтверждение удаления. Удаление не затрагивает библиотеку/процессы. Главная/палитра/текстовый router используют динамические названия.
- Настройки v4 совместимы: добавлены необязательные флаги и источник шаблона; старые режимы, действия, команды и библиотека сохранены.
- C НЕ реализован: подтверждение выбора окон для штатного закрытия и общий механизм переключения требуют отдельной проверки на Windows (принадлежность процессов, диалоги сохранения, PID reuse, отмена).
- D1–D5 НЕ реализованы: нет подключённого offline-распознавания, лицензированной русской модели, аудиопакета SOL, голосовых настроек и wake phrase. Микрофон не используется. Динамические имена подготовлены существующим текстовым router, это не голосовая поддержка.
- E/F частично: сохранён интерфейс, новые A/B сценарии проверены локально. Реальные процессы/браузер/ассоциации и UX Windows требуют ПК; голосовые/переключательные тесты отложены вместе с C/D. Весь SOL Core не считается готовым.

### Надёжность запуска Windows — исправлено, runtime-проверка ожидается

- Доказанные дефекты: Mode Engine игнорировал `app.skipIfRunning` и всегда передавал `true`; совпавший EXE-процесс считался открытым приложением без проверки UI. Это объясняет возможный ложный «Уже работает» при фоновом Steam, но состояние конкретного ПК без диагностики не подтверждено.
- Сохранённая настройка теперь соблюдается. Идентичность проверяется через volume GUID/file ID (включая hard-link/symlink и case-sensitive каталоги), а не имя или только lowercase-путь. Системные/собственные процессы не подменяют выбранный EXE.
- «Уже работает» требует подтверждённого EXE и обычного доступного top-level окна; свёрнутое окно на панели задач учитывается. Скрытые/tool/cloaked/нулевые служебные окна и зависшие окна не считаются UI. Фон/неполная проверка — отдельный «Не удалось определить состояние», без автоматического повторного запуска; можно явно выключить проверку в библиотеке.
- UI, размещённый сторонним приложением в другом helper-процессе, не объявляется доказанным. Ресурсы читаются с ограниченными правами, ручной запуск не меняет пользовательский путь и не завершает процессы.
- Оба вида запуска EXE используют CreateProcessW с точным lpApplicationName, без пользовательской command line, без наследования handles. Для сворачивания — STARTUPINFO/STARTF_USESHOWWINDOW/SW_SHOWMINNOACTIVE, только нового процесса. Подтверждённое сворачивание не обещается.
- Структурированные результаты/ошибки содержат фактический EXE, canonical path, библиотечный ID, причину проверки, PID/число окон и код Windows. В интерфейсе это блок «Подробнее», без dump окружения, URL-токенов или секретов.
- Windows launch core выделен из Tauri command-wrapper, чтобы native integration tests проверяли тот же производственный код. В validation crate согласованы windows-sys features и serde; предыдущая E0433 не возвращается.
- Добавлены отдельные Windows-интеграционные тесты с настоящим кооперативным Win32 fixture: закрыт/видим/фон/свёрнут, одинаковые EXE-имена в разных каталогах, hard-link, повторный запуск и код отсутствующего EXE. См. `tests/rust-validation/WINDOWS_TESTS.md`.
- В Linux эти Windows tests только компилируются/линкуются. Steam/Discord/Telegram/браузер, GUI в helper-процессах и фактический foreground/minimize требуют ручной Windows-проверки. Проблема не объявляется окончательно решённой. Windows CI вручную не запускается.

### Windows CI #38447613738 — исправление гонок, native-проверка ожидается

- В default parallel Cargo run три теста использовали `same-name.exe` и могли видеть стартующие/завершающиеся фикстуры друг друга. Тесты теперь сериализуют только свой общий сценарий; проверки реальных EXE, фонового/видимого/свёрнутого окна, другого каталога и hard-link сохранены. Сигнал готовности публикуется атомарно.
- Production inspection больше не превращает достоверно завершившийся процесс в Unknown: перепроверяет exit state после неудачного чтения образа/идентичности, пропускает исчезнувший snapshot PID и завершившиеся подтверждённые handles. Живой недоступный кандидат остаётся Unknown; сопоставление EXE/окон и безопасный запуск сохранены.
- Assertions выводят настоящий LaunchReport/Inspection, диагностика неопределённости указывает API/этап и PID. Без полного журнала (API Forbidden) нельзя утверждать, что именно эта гонка объясняет оба падения указанного CI.
- Локальные проверки: 46 TypeScript-тестов, 10 portable Rust-тестов, TypeScript/Vite build; Windows GNU integration EXE и Tauri check проверяются компиляцией, не исполнением. Native Windows/MSVC CI требует повторной проверки после публикации; вручную CI не запускается, релиз готовым не объявлен.
- Голосовая часть B1–B5 отложена до подтверждения части A на Windows. Vosk, русская модель, захват микрофона и аудиопакет пока не подключены; способ их установки ещё не реализован. Данные, UI, трей/single-instance и Mode Engine не менялись.
